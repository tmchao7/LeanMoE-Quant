### R3 — “没有 token 数据”也可能被认为 tokens_equal

### R4 — 尾 canary 没包住最后一次处理臂，少量均值不足以判小收益

**位置**：`tools/profile_graph.py` 的 `[A,B] * rounds`、`base[-1]` 与 `--ab-rounds` 默认两对。
实际顺序是 A/B/A/B，所谓尾 canary 是第三次 run；最后一次 B 发生在它之后。
这与首尾同格的协议不符。新增 median 没有补上 MAD、相邻配对差与胜率；两对只能作为探索性信号。
同进程也仍会逐 run 重载模型，需把模型加载后的 warmup 与稳态记录清楚。

**后续验证**：用 fake `_invoke` 记录实际顺序；在最后一个 B 注入异常，检查轮次是否仍可能被首尾 A 放过。
**修复方向**：A/B 交错后另测尾 A，明确 canary 是否纳入 arm 汇总；正式判断补 median/MAD 与逐对胜率，
每项保留单变量。不自行给新收益判据拍阈值或宣布小收益显著。

### R6 — RoPE 对 sin 使用了 cos 的 stride，并复用 q 的输出 dtype

**位置**：`src/lemoq/kernels/rope.py:117`、`:118`、`:125`、`:172`、`:191`。
`sin_ptr` 也按 `sc_d` 索引，而 host 只传 cos 的末维 stride；守卫只查两者 shape。
例如 cos 连续、sin 来自 `(1,1,2D)[...,::2]`，shape 相同而 stride 不同，可通过守卫。
另有 q/k dtype、cos/sin device 的一致性未查；k 也用 q 的 `DTYPE` 舍入。
守卫在检查 ndim 前先取 `shape[0]`，零维输入也不能按声明回退。

**影响范围**：正常模型调用通常同 dtype、同布局、同设备；本轮未发现已录主路径必然触发。
**后续验证**：CPU mock 检查这些输入是否进入 launch；GPU 比较不同 cos/sin stride、混合 dtype、
合法 transpose 输入与 HF 输出。**修复方向**：支持独立 stride/dtype 或在 launch 前显式回退，
不能仅靠 `.contiguous()` 悄悄增加热路径代价。数值容差不变。

### R7 — attention wrapper 承诺的布局比 kernel 实际支持的宽

**位置**：`attn_decode.py:525`、`:555`、`:586`；`_attn_triton.py:83` 附近的 `base`。
只检查末维 stride=1，kernel 却假定序列 stride=D，并给 K/V 共用 K 的 head stride。
`cache[:,:,::2,:]` 满足末维连续但不满足序列步长；K/V 形状相同也不能推出 head stride 相同。
reshape 若产生副本，继续传原始 k.stride 也需核对。q/k/v 同 device 与 head_dim/batch 契约未完整封闭。
设备 `filled_len` 只检查形状/dtype/device，没有保证值在 `[0,seq_len]`；超容量时 kernel 可读过 buffer。

**影响范围**：内置 StaticCache 正常布局与 session 容量检查是现有保护；主要是公有 helper/未来 KV 改造风险。
**后续验证**：同 shape 不同 K/V stride、序列切片、长度 0/1/末尾/超界；
CPU oracle 路径与 mock launch 分开检查，GPU 后用独立 dense oracle 和 compute-sanitizer（已有才用）。
**修复方向**：明确限定布局，或传齐实际 stride；设备长度在图内采取安全处理，避免引入 host `.item()` 同步。

### R8 — routing 的“等权专家可交换”理由遗漏 top-k 边界

**位置**：`_routing_triton.py` 模块说明与 `tl.argmax`；`tests/test_routing_fusion.py:70`。
融合实现平局取最低 index；torch.topk 不保证 tie 的索引稳定。
**同一专家集合换顺序**与**边界平局换掉一个专家**不同：后者的专家输出一般不相等，不能由权重相等推出模型等价。
现有随机样例与“排序后比较集合”的测试未特意构造 kth/(k+1)th 平局。

**后续验证**：64 个相等 logits、只在第 8/9 名平局、fp16 舍入导致的 tie、softmax 下溢、近邻非平局；
专家输出刻意设成不同常量，比较最终 MoE 输出，不能只比路由概率。
**修复方向**：保持候选默认关闭，先确认真实门数据上的发生率和输出差异；
若必须变更 tie 策略，参考与候选的语义及新正确性证据要明确，不把算法变更伪装为等价融合。
依据：[PyTorch 2.8 topk](https://docs.pytorch.org/docs/2.8/generated/torch.topk.html)。

### R9 — routing 空 token 仍启动 kernel

**位置**：`_routing_triton.py:100`、`:104`、`:110`。
`T=0,E=64` 时输出为 `(0,K)`，grid 却取 `max(T,1)`；kernel 的 token 行没有 `t<T` 掩码，
仍读 logits、写 top_i/top_w。E/top_k 检查不能拦住此输入。
正常 decode T=1 不触发，不据此否定已测路径。

**后续验证**：先 CPU mock 确认是否 launch；GPU 在安全隔离进程中确认边界，避免污染后续 CUDA context。
**修复方向**：空输入返回空输出或显式拒绝，且在 launch 前发生。

### R10 — skip-mask-fill 没有绑定到“所有消费者均不读 mask”的保证

**位置**：`benchmarks/cudagraph.py:482`、`:614`、`:700`、`:735`；
`tools/profile_graph.py` 允许 `--attn sdpa --ab-mask-fill`。
session 直接按全局 env 跳过更新，不确认已捕获的 backend 是否忽略 mask。
eager/SDPA 需要 mask，新 token 加入而 mask 停留在 capture 时刻会有状态错误。
现有 runner 的 graph/eager correctness 门是保护，**应先确认它能拦截**，不能说这种组合已经悄悄发布了错误性能。

**修复方向**：capture 时绑定明确能力/实现记录；不满足忽略 mask 条件则拒绝候选或保留更新，

### R11 — 同路径自洽和重复 token 的轨迹不能单独完成候选正确性验收

**位置**：`benchmarks/runner.py:1028` 的同路径参照、`:1039` 的 informational HF 对照；
`run_cudagraph` 的全 1 prompt；`tests/test_fused_rope.py:128`。

共享错误也可自洽；相同 argmax 更不能证明 logits 误差或实际专家路径足够小。
RoPE GPU K1 的误差相对 oracle/基线的比例检查只对 q 做，k 只有 allclose，覆盖不对称。

**后续验证**：复用既有自然文本 prompt 集（不重跑已完成 cells），
对每个候选逐项比较独立 HF/数学 oracle、q 和 k、logits KL/top-1、轨迹、路由及 cache 内容。
残差 epilogue 单独加入 `fp16(fp16(acc)+residual)` 与 `fp16(acc+residual)` 的舍入边界反例。
**修复方向**：候选采纳前补独立证据；若实现/适用配置改变，旧引用门不是自动覆盖新实现。
现有 E2/E7 和 fused RMSNorm 已有独立门与记录，本轮不重判这些已完成结论。

### R12 — occupancy 兜底参数和完成状态容易被过读

**位置**：`tools/occupancy_probe.py:56` 的 `(12,0)` fallback（shared=228 KiB）、`:109` 的 `_limits`、
`:371` 的 `any_measured`。官方 Blackwell tuning 表中 sm_120 的 per-SM shared capacity 是 128 KB，
per-block 上限 99 KB；不能把 sm_90/sm_100 的 228 KB 直接复制过来。
运行时属性能覆盖该值，所以必须先查工件 inputs 才能判断历史估计是否受影响。
工具还允许只有一个 kernel family 成功时整体 done，不能把 done 直接读成所有 family 齐全。

**后续验证**：mock 缺少属性的 sm_120、未知设备、一个 subject 成功其余失败；
只读核对现有 `results/occupancy.json` 的 inputs/逐族状态。
**修复方向**：修正可追溯 fallback 并显式报告覆盖率；保持 estimate/upper，不把估计升级为实测。
本轮只读核对：现有工件三族均为 `measured_estimate`，各 config 的 `inputs.smem_per_sm=102400`，
没有使用 228 KiB 兜底；因此**没有证据认为这处兜底错误影响了当前已录三族上界**。
不在本轮重新测量或自动作废。
依据：[NVIDIA Blackwell tuning §1.4.1.1](https://docs.nvidia.com/cuda/blackwell-tuning-guide/index.html)。

### 优化规格的误导性结论（与运行时 bug 分开）

`FUSION_OPPORTUNITIES.md` 需要在实际做 F2/F3 前修正以下推理；本轮只在调研/本报告标注，未执行这些优化。

- F2 的 `grid×warps/SM` 不能证明实测 occupancy 或唯一瓶颈；更大 grid 也不能保证 hidden 只读一次。
- F3 不能把 fp16 中间舍入删掉，只讨论 `a+b` 与 `b+a` 不足以保证等价；“零额外字节”应改为明确的净读写账。
- “单消费者才能融合”不是普遍定理，要看真实张量依赖、物化成本和 live range。
- persistent kernel 与 graph 不是可一概宣布互斥的类别；GPUOS 的 host 队列生命周期需单独分析。
- “autotune 全部不兼容 graph”过强；本仓禁止新增 autotune 仍照办，技术理由应限定在 capture 内首次调优等情形。
- 不能把 H100/训练/服务吞吐的论文收益，移作 5090 batch=1 decode 的预期实测值。

外部依据与具体适用限制见 [FUSION_RESEARCH §5](../../reference/FUSION_RESEARCH.md#5-二次复核怎样把资料变成可执行的-review)。

### P1 — A/B 验收缺 busy 自检与 host_share 污染判据（方法学，高）

**位置**：`tools/profile_graph.py` `_run_env_ab`（+ `run_routing_ab` / `run_mask_fill_ab` / `run_fused_rope_ab`）。

**现象**：
1. 金丝雀只比较基线臂 wall 的首尾两次（`base[0]` vs `base[-1]`），**没有 gpu_busy 跨臂稳定性自检**——而 fused-rope 的 Journey log ① 自己就建议补它（第 1 轮 wall 金丝雀 5.923% VOID，busy 却纹丝不动）。
2. AGENTS §6 的图格污染判据（`host_share_pct > 5` ⇒ 污染）**没有机械化**进 `_run_env_ab`：`results/fused_rope_ab.json` 4 个 run 里 3 个 host_share 5.7/6.3/7.8% 仍判 `measured`，而 `tools/round_canary --graph` 的同一条规则会判 VOID。skip-mask-fill Journey log ④ 已指出"treatment 本身降 host 时判据应看 busy 跨臂不变"，但代码里两个版本的判据都没落实。
3. `tokens_equal` 在退化轨迹下近乎空判据：fused_rope_ab 的 4 个 run 全是 `[5474]×32`（合成 prompt 退化轨迹），序列全等不构成强证据——routing Report 已自认，但工具不输出任何警告。

**为什么是问题**：F1 的采纳决策（0.24 ms 已测收益是否兑现）完全依赖这三份 A/B 的判定质量；判定机器比协议松，等于把"测过的"当成"验过的"。

**验证**：构造 fake `_invoke` 的单测——busy 漂移超阈、host_share>5、token 退化三种情形下 payload 应有对应字段/警告。

**修复**：`_run_env_ab` 增加 ① `busy_drift_pct`（基线臂首尾 busy）与 `busy_stable` 字段；② 每 run `host_share_pct` 超过 5% 时 payload 记 `host_share_warnings`（**先只警告不改判定**——skip-mask-fill 的判据争议未决，改判定语义需用户批准）；③ token 序列全同时记 `degenerate_trajectory: true` 警告。判定逻辑保持现状（`status` 语义不变），只加观察字段。

**验收**：新单测绿；旧单测（`test_ab_routing_verdict` 等）不回归；四门绿。

### P2 — `_run_env_ab` 遇 `wall_p50_ms=None` 直接崩溃（中）

**位置**：`tools/profile_graph.py` `_run_env_ab` 的 `mean_a = sum(r["wall_p50_ms"] for r in base) / len(base)`。

**现象**：任一 run 的 `wall_p50_ms` 为 None（gap 不完整时 `_extract_ab` 会返回 None），`sum()` 抛 TypeError，被 `main()` 的 `except` 吞成 `status=failed`——丢失整轮已跑的 run 数据，且不是协议要求的 fail-closed（应判 `invalid` 并写明原因，像金丝雀缺失那样）。

**验证**：fake `_invoke` 让第二轮返回 `wall_p50_ms=None`，断言 payload `status=invalid` 且 `reasons` 含原因，而不是抛异常。

**修复**：None 容错——任一 wall/busy 缺失 ⇒ `reasons` 记"指标缺失"、status=invalid、均值字段为 None。

**验收**：新单测绿、旧单测不回归、四门绿。

### P4 — fused rope 守卫不检查 `position_ids`（中）

**位置**：`src/lemoq/kernels/rope.py` `apply_rotary_pos_emb_fused` / `_decode_shape_guard`。

**现象**：签名与 HF 一致收 `position_ids`，但 kernel 路径**直接忽略它**：HF 的 `apply_rotary_pos_emb(q, k, cos, sin, position_ids=None, ...)` 在 `position_ids` 非 None 语义下按位置索引 cos/sin，而 fused 路径拿到什么用什么。守卫检查了 shape/dtype/CUDA，唯独没查 `position_ids`。当前唯一 call site（`attn_decode._decode_forward_impl`）不传 position_ids 且 cos 已按位置索引 ⇒ **现状安全**；但这是"同签名、暗降级"的契约陷阱：未来任何 call site 传 position_ids 就会静默算错。

**验证**：单测——`position_ids` 非 None 时 `apply_rotary_pos_emb_fused` 走 `_hf_apply` 回退（可用 monkeypatch 断言回退被调用）。

**修复**：`_decode_shape_guard`（或调用前）加 `position_ids is not None ⇒ 回退 HF`；docstring 注明。

**验收**：新单测绿、`test_fused_rope.py` 全部不回归、四门绿。GPU K1 回归并入下次上机（改动只增回退分支，不动 kernel 本体）。
