### P1 — A/B 验收缺 busy 自检与 host_share 污染判据（方法学，高）

**位置**：`tools/profile_graph.py` `_run_env_ab`（+ `run_routing_ab` / `run_mask_fill_ab` / `run_fused_rope_ab`）。

**现象**：
1. 金丝雀只比较基线臂 wall 的首尾两次（`base[0]` vs `base[-1]`），**没有 gpu_busy 跨臂稳定性自检**——而 fused-rope 的 Journey log ① 自己就建议补它（第 1 轮 wall 金丝雀 5.923% VOID，busy 却纹丝不动）。
2. AGENTS §6 的图格污染判据（`host_share_pct > 5` ⇒ 污染）**没有机械化**进 `_run_env_ab`：`results/fused_rope_ab.json` 4 个 run 里 3 个 host_share 5.7/6.3/7.8% 仍判 `measured`，而 `tools/round_canary --graph` 的同一条规则会判 VOID。skip-mask-fill Journey log ④ 已指出"treatment 本身降 host 时判据应看 busy 跨臂不变"，但代码里两个版本的判据都没落实。
3. `tokens_equal` 在退化轨迹下近乎空判据：fused_rope_ab 的 4 个 run 全是 `[5474]×32`（合成 prompt 退化轨迹），序列全等不构成强证据——routing Report 已自认，但工具不输出任何警告。

**为什么是问题**：F1 的采纳决策（0.24 ms 已测收益是否兑现）完全依赖这三份 A/B 的判定质量；判定机器比协议松，等于把"测过的"当成"验过的"。

**验证**：构造 fake `_invoke` 的单测——busy 漂移超阈、host_share>5、token 退化三种情形下 payload 应有对应字段/警告。

**修复**：`_run_env_ab` 增加 ① `busy_drift_pct`（基线臂首尾 busy）与 `busy_stable` 字段；② 每 run `host_share_pct` 超过 5% 时 payload 记 `host_share_warnings`（**先只警告不改判定**——skip-mask-fill 的判据争议未决，改判定语义需用户批准）；③ token 序列全同时记 `degenerate_trajectory: true` 警告。判定逻辑保持现状（`status` 语义不变），只加观察字段。

**验收**：新单测绿；旧单测（`test_ab_routing_verdict` 等）不回归；四门绿。

### P2 — `_run_env_ab` 遇 `wall_p50_ms=None` 直接崩溃（中）

**位置**：`tools/profile_graph.py` `_run_env_ab` 的 `mean_a = sum(r["wall_p50_ms"] for r in base) / len(base)`。

**现象**：任一 run 的 `wall_p50_ms` 为 None（gap 不完整时 `_extract_ab` 会返回 None），`sum()` 抛 TypeError，被 `main()` 的 `except` 吞成 `status=failed`——丢失整轮已跑的 run 数据，且不是协议要求的 fail-closed（应判 `invalid` 并写明原因，像金丝雀缺失那样）。

**验证**：fake `_invoke` 让第二轮返回 `wall_p50_ms=None`，断言 payload `status=invalid` 且 `reasons` 含原因，而不是抛异常。

**修复**：None 容错——任一 wall/busy 缺失 ⇒ `reasons` 记"指标缺失"、status=invalid、均值字段为 None。

**验收**：新单测绿、旧单测不回归、四门绿。

### P3 — A/B 均值口径未声明（随 P1/P2 修复，中→低）

**位置**：同上。`mean_wall_*` 是 2 个 run 的算术均值（每 run 内部已是 p50）。样本量只有 2 时 mean=median，但契约上应声明口径（工具输出 `stat: "mean_of_run_p50s"`），并优先报中位数（`ab_rounds>2` 时均值易被单轮污染）。

**修复**：输出补 `stat` 字段 + `median_wall_*`；报告两个口径。

**验收**：单测断言字段存在；四门绿。

### P4 — fused rope 守卫不检查 `position_ids`（中）

**位置**：`src/lemoq/kernels/rope.py` `apply_rotary_pos_emb_fused` / `_decode_shape_guard`。

**现象**：签名与 HF 一致收 `position_ids`，但 kernel 路径**直接忽略它**：HF 的 `apply_rotary_pos_emb(q, k, cos, sin, position_ids=None, ...)` 在 `position_ids` 非 None 语义下按位置索引 cos/sin，而 fused 路径拿到什么用什么。守卫检查了 shape/dtype/CUDA，唯独没查 `position_ids`。当前唯一 call site（`attn_decode._decode_forward_impl`）不传 position_ids 且 cos 已按位置索引 ⇒ **现状安全**；但这是"同签名、暗降级"的契约陷阱：未来任何 call site 传 position_ids 就会静默算错。

**验证**：单测——`position_ids` 非 None 时 `apply_rotary_pos_emb_fused` 走 `_hf_apply` 回退（可用 monkeypatch 断言回退被调用）。

**修复**：`_decode_shape_guard`（或调用前）加 `position_ids is not None ⇒ 回退 HF`；docstring 注明。

**验收**：新单测绿、`test_fused_rope.py` 全部不回归、四门绿。GPU K1 回归并入下次上机（改动只增回退分支，不动 kernel 本体）。

### P6 — skip-mask-fill 模式下 mask 是陈旧数据，未文档化（低-中）

**位置**：`benchmarks/cudagraph.py:614-635` `_set_step_inputs(skip_mask=True)` 分支。

**现象**：`LEMOQ_SKIP_MASK_FILL=1` 时 `attention_mask` 在图外不再更新（`filled_len` 照更）。graph 臂不读 mask（tokens_equal 门验证过），但若同一 session 内有人消费 `buffers.attention_mask`（比如外部做 eager 对照、或未来加后处理），会拿到陈旧 mask 而不自知。`replay_at_position()` 尤其明显：position 变了、mask 没变。

**验证**：单测——skip 模式 replay 后 `buffers.attention_mask` 保持旧值，而 `filled_len` 已更新；`decode_eager`（默认 skip_mask=False）永远重填。

**修复**：代码注释 + docstring 明确契约："skip 模式下 `attention_mask` 是未定义的陈旧数据，禁止任何图外消费者读它"；单测钉住 eager 路径永远重填。

**验收**：`tests/test_skip_mask_fill.py` 扩展绿；四门绿。
