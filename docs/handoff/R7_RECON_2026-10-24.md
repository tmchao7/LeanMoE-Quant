## 0. 结论先行

**两条外部锚定路线在 5090 上都可行**；推荐 **方案 A（vLLM）**，备选 **方案 B（llama.cpp）**。
共同前置：装机/构建需用户同意（AGENTS §6 红线；§7 允许装机但不得在实验中途），
且 vLLM 必须装在**独立 venv**（它会带自己的 torch ≥2.9，不得动计费环境的 torch 2.8.0+cu128）。
建议排 S1/S2 之后的一个 ≤1 h 独立小窗口；产出进记录（新 EXP 或 ISSUES 附录），
**不进 `GATE_CITATIONS`**（口径不同，见 §4）。

## 1. vLLM 路线（推荐）

| 事实 | 证据 |
| --- | --- |
| OLMoE 官方支持：`OLMoEForCausalLM` 在 supported_models 列表（含 `allenai/OLMoE-1B-7B-0924`），v0.6.x 起集成 | [vLLM supported models](https://docs.vllm.ai/en/latest/models/supported_models)、[allenai/OLMoE README](https://github.com/allenai/OLMoE)（"integrated into vLLM, SGLang, llama.cpp, transformers"）、[issue #8170](https://github.com/vllm-project/vllm/issues/8170) |
| 5090（SM120）可用：社区实测 torch 2.9.0 + cu128 轮子是已确认组合；NVFP4 on SM120 自 v0.12.0 | [论坛 5090 配置帖](https://discuss.vllm.ai/t/vllm-on-rtx5090-working-gpu-setup-with-torch-2-9-0-cu128/1492)、[SM120 吞吐与版本回退帖](https://discuss.vllm.ai/t/sm120-rtx-pro-4000-6-5x-throughput-gain-and-v0-18-1-regression-findings/2525) |
| 版本选择：**0.17.x 优先**——v0.18.1 在 SM120 有社区报告的吞吐回退 | 同上 SM120 帖 |
| 本机驱动满足：595.71.05 ≥ 社区建议的 590.48+ | `results/machine_probe.json` / AGENTS §7 |

跑法（batch=1、对齐我们的两臂）：

```bash
python -m venv /root/lemoq-vllm-venv && source .../bin/activate   # 独立 venv
pip install "vllm==0.17.*"                                        # 自带 torch≥2.9+cu128
vllm bench latency \
    --model /root/autodl-tmp/ms/models/allenai--OLMoE-1B-7B-0924/snapshots/master \
    --dtype float16 --batch-size 1 \
    --input-len 1024 --output-len 64 --num-iters 30 \
    --output-json vllm_latency_fp16_graph.json
# 再跑一遍加 --enforce-eager，得"图内/无图"两臂（与我们 eager/cudagraph 的区分对齐）
```

参数依据：[`vllm bench latency` 文档](https://docs.vllm.ai/en/latest/cli/bench/latency/)——
`--batch-size`（默认 8，须改 1）、`--input-len/--output-len`（默认 32/128）、
`--num-iters-warmup 10 / --num-iters 30`、`--dtype`、`--enforce-eager`、`--output-json`。
输出以平均时延为主；若需分位以 `--output-json` 原始数据为准（文档页未列分位口径，如实注明）。

成本：venv + 引擎缓存 ≈ 10–15 GB 磁盘（`/root/autodl-tmp` 有空间即可）；模型走本地快照，
不触发下载（`HF_ENDPOINT` 已配镜像）。

## 2. llama.cpp 路线（备选）

- OLMoE 已被 llama.cpp 官方集成（[allenai/OLMoE README](https://github.com/allenai/OLMoE)
  给出安装/量化/自转指引）；**需较新 build**（老版本不认 `olmoe` 架构——Reddit 有旧 build 报错帖，
  本网络不可达，不列链接；README 为准）。
- **checkpoint 错位是主要坑**：官方 GGUF 是 `OLMoE-1B-7B-0125-Instruct`，bartowski 有
  `0924-Instruct`——都不是我们的 **0924 base**（HF 链接本网络不可达；以 README 的
  `convert_hf_to_gguf.py` 自转为可行路径，本地快照即可转，无需下载）。
- 跑法：`llama-bench -m olmoe-f16.gguf -p 1024 -n 64 -r 5`（[llama-bench README](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md)）；
  外部锚用 **F16 gguf**（不要量化版，否则锚的是别人的量化）。
- 成本：cmake 构建 ≈ 10 min + F16 gguf ≈ 模型同尺寸磁盘。

## 3. 方案对比与推荐

| | A：vLLM bench latency | B：llama-bench |
| --- | --- | --- |
| 同模型可行性 | ✅ 本地 0924 快照直接加载 | ⚠️ 需自转 gguf（base 无现成） |
| 口径贴近度 | 更近：HF 权重、fp16、batch=1、可关 eager | 较远：自有 kernel 栈 + 采样 |
| 装机成本 | pip venv（~10–15 GB） | 构建 + gguf 转换 |
| 风险 | v0.18.1 SM120 回退 ⇒ 钉 0.17.x | 旧 build 不认 olmoe ⇒ 用新 tag |

## 4. 口径警告（写进未来记录的引言，不得省）

外部锚**不是**同口径 A/B：vLLM/llama.cpp 的"一步"含各自的采样/logits 处理、KV 布局与
kernel 选择，与我们"图内一步全链（不含采样）"的 per-token p50 **不可直接比大小**。
它的作用只有一个——回答"**同一个模型、同一张卡上，业界实现大概在什么量级**"，
作为对自参照（所有基线都是本仓自己实现的）的修正。对比表必须带口径列；
结论只允许"量级/同数量级/差一个量级"式表述，禁止写成"我们比 vLLM 快/慢 x%"。

1. 是否批准在 5090 装 vLLM（独立 venv，~10–15 GB，不动计费环境）；
2. 是否批准构建 llama.cpp（若选 B 或 A+B）；
3. 窗口：建议 S1/S2 之后的独立 ≤1 h 小窗，产出进记录、不进 `GATE_CITATIONS`。
