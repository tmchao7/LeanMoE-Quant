## P1 — 测量协议（本地可改工具/文档）

### P1-1 同进程交错 A/B 的 `host_share` 会随轮次累积

- **现象**：F2 的同进程交错 A/B 三轮全 VOID；同一格在进程内**第一次**跑是 3.2–3.6%，
  之后升到 5.5–7.1%。
- **证据**：`/root/autodl-tmp/lemoq-w4-data/f2-ab/packed-qkv-ab*.json`（7 次 run 的 host_share 序列）。
- **根因（假设）**：同一进程里连续跑多次完整 `run_cudagraph`（重复加载模型/捕获图/分配器状态），
  每步 host 时间上升；与同租户无关（容器内只有我们的进程，GPU 空闲）。
- **已验证的替代**：每臂**独立进程**的同轮相邻 A/B —— off 1.9541/1.9529/1.9538，on
  1.8636/1.8575/1.8581，host 3.5–4.2%，3/3 对，canary −0.015%。
- **本地可做**：给 `tools/profile_graph.py` 的 `_run_env_ab` 加"每臂子进程"模式（或在
  多轮模式下把 host_share 的累积作为已知偏差写进 docstring）；并在
  `docs/reference/METRICS.md` 记录"长时间同进程 A/B 的 host_share 会漂"。

### P1-2 cgroup 限流与 torch 线程

- **证据**：`/sys/fs/cgroup/cpu.stat`：`nr_throttled=5408 / nr_periods=71580`，
  `throttled_usec=16.2 s`；配额 `cpu.max=1600000 100000`（16 CPU）。
- **推断**：torch/加载阶段的短时多线程突发超过 16 CPU 配额（不是长期饱和）。
- **本地可做**：在 `docs/reference/SERVER_RUNBOOK.md` 记录"计时前把线程数钉死"
  （`OMP_NUM_THREADS` / `torch.set_num_threads`）作为候选；**未验证前不改默认**。

### P1-3 宿主机负载不可控（记录，不解决）

`uptime` 的 load 13–21 是**宿主机**（128 核）上的其他租户，容器内看不到也管不了；
它只影响 host 侧抖动。记录在 runbook 即可。
