## 9. E6 KV INT8 续作指引（2026-10-25 深夜写，**接手模型从这里开始**）

**已完成（全部已推送，CI 绿）**：
- 写路径 `kv_int8_write` K 门 4/4 逐位（`2269c11`）；读路径 int8 split-KV parity 4/4 vs
  fp64 oracle 1e-3（`0f1a025`+`8a844d6`）——含部分填充/多 split/cache 写散布/bulk 量化 = **8/8**；
- 接线全落：`LEMOQ_KV_INT8`（第七开关，默认关）+ `KV_INT8_GATE_CITATIONS`（**空表
  fail-closed**：开关开+无门实测 ⇒ runner 加载前拒绝）+ correctness 合取 + `kv_int8_effective`
  payload 字段 + probe `e6_kvint8` 臂组（**轨迹口径**：decode 步 logits vs fp16 轨迹，
  teacher forcing 是 prefill 对 KV 扰动哑）；
- 记录：`experiments/EXP-p5-01-kv-int8.md`（假设/阶梯/K 门 API/已踩坑全在里面）。

**★★ 首轮门测量无效（假 0），根因已定位——这是接手要修的第一件事**：
`results/EXP-p5-01-kv-int8/gate_e6_kvint8*.json` 里 `kv_int8_runs=0`、KL 恰 0.0 = int8 从未
执行。根因：**probe 的贪心轨迹用 HF DynamicCache**（`out.past_key_values`），而换核 decode
前向 `_decode_forward_impl` 在 `filled is None`（DynamicCache 无 `_lemoq_filled_len`）时
**显式回退 HF 原路** ⇒ int8 分支从未进入。
**修法**：probe 的 e6 臂轨迹改用 StaticCache 会话——照 `benchmarks/` 里
`StaticCacheDecodeSession` 的机制：建 `StaticCache(max_cache_len=ctx+max_new, fp16)` +
设备张量 `_lemoq_filled_len` 挂上 cache 对象、每步 `fill_(t)`、forward 传
`cache_position`。参考/臂同一条会话路径，参考走 fp16（开关关）、臂走 int8（开关开）。

**之后照 F5 的采纳模板走**：

   （工件 `results/EXP-p5-01-kv-int8/`，**测试钉死**照 `test_lmhead_gate_citations` 模式）；

   预期 −150~170 µs）；验证 on 臂 payload `kv_int8_effective=True`（**首轮就验，别等刷新**）；

**本窗踩坑清单（接手必读，全是真踩过的）**：
1. **reshape 后 3D 的 `stride(1)`=D 不是 head stride（S·D）**——E6 读路径首跑 head 0 恰好
   对、其余头全错（`0f1a025` 修）；fp16 路径传 4D stride(1) 所以历史上没踩中；
2. **测试参考的 batched 广播串头**：`(1,H,·)` 与 `(H,·)` 混用会在头维串数据——K 门参考
   必须**逐头 1D 循环**（同日三犯，全部把 kernel 冤枉成错的）；
3. **量化约定的除法 scale**：fp32 除、fp16 存——参考用 fp16 scale 做除法会有 1-ulp 代码差；
4. **V scale 不得折进 softmax 分母**（l=Σp，否则输出把 vs 消掉）——CPU 测试有反证断言；
5. probe 轨迹 = DynamicCache ⇒ 换核 decode 回退（本节根因）；
6. pytest 接 `| tail` 吞退出码（**三犯**）——门命令一律不接管道；
7. 翻默认后测试的 off 语义要显式 `env=0`（N6：钉机制不钉默认值）；
